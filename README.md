# 城市菜市场电子秤检定与短斤少两投诉服务

基于 **Kotlin + Ktor + PostgreSQL** 的菜市场电子秤计量监管服务：设备登记、规则引擎生成抽检任务、现场抽检与误差超标处置、消费者短斤少两投诉与交易可信度判断、离线交易补传与人工复核、处罚-申诉-整改-复检-封签更换-回访闭环、公示与市场评分、处罚后变化追踪与年度治理材料。

## 原始需求

> 开发城市菜市场电子秤检定与短斤少两投诉服务，可采用 Kotlin、Ktor 和 PostgreSQL。市场管理方为每台电子秤登记设备编号、摊位、经营品类、检定证书、有效期、封签照片和联网状态。监管人员巡检时，服务根据检定到期、投诉次数、交易峰值和摊位历史处罚生成抽检任务。抽检记录包括标准砝码重量、秤显示值、误差、封签状态、摊主确认和现场照片；误差超标会触发停用、复检或处罚流程。消费者投诉时，服务收集购买时间、摊位、商品、标称重量、复称重量、付款记录和现场照片，并匹配对应电子秤和当天交易记录。若摊位临时更换电子秤、多人共用一台秤、网络离线或检定证书过期，服务要判断交易是否可信。处罚结论不仅影响摊主罚款，还会改变市场信用、后续抽检频次和公示内容；整改完成后，复检结果、封签更换和投诉回访要回到同一台秤的监管档案。服务还要支持按市场、摊位、设备和投诉人维度追踪处罚后变化，监管人员能判断整改是否真的减少短斤少两。服务还要把公示、申诉、复检和市场评分串起来，形成监管部门可追踪的年度治理材料。

## 技术栈

- 后端：Kotlin 1.9 + Ktor 2.3（Netty、Sessions、kotlinx.html 服务端渲染）
- 数据库：PostgreSQL 16（Exposed ORM + HikariCP）
- 部署：多阶段 Dockerfile（非 root 用户 + HEALTHCHECK）+ docker compose

## 启动方式（验证 = 宿主 docker compose up）

```bash
cp .env.example .env        # 可选，默认即可
docker compose up -d --build
docker compose ps           # app 健康检查通过后
docker compose port app 8080   # 查看实际发布的宿主端口
# 浏览器访问 http://localhost:<端口>
```

- 仅应用服务发布到宿主端口（compose 中 `${CC_PUBLISH_PORT}:8080`，未设置时按 `.env` 的 `CC_PUBLISH_PORT`）；PostgreSQL 只在 compose 内部网络，应用通过服务名 `db` 访问。
- 首次启动自动建表并写入演示数据（`SEED_DEMO=false` 可关闭）。
- 验证结束：`docker compose down`（加 `-v` 同时清空数据卷）。

## 关键业务流（建议按序验证）

1. **设备登记**：`admin` 登录 → 电子秤台账 → 登记新秤（可上传封签照片）。
2. **抽检任务生成**：`regulator` → 监管工作台 → 「立即生成抽检任务」。规则评分：证书过期+50 / 30天内到期+30 / 90天内+10；近90天投诉≥3次+30 / ≥1次+15；日均交易≥100笔+15 / ≥50笔+8；历史处罚≥2次+25 / 1次+10；离线+10；≥30 分生成任务。
3. **抽检录入**：任务列表 → 录入抽检（标准砝码 1000g、秤显示值、封签状态、摊主确认、现场照片）。误差超过 ±0.5% → 自动停用设备并开出处罚（金额随误差浮动）。
4. **投诉与可信度判断**：`consumer` 提交投诉 → 系统自动匹配摊位当前秤与当天交易流水，并标记可信度风险：检定证书过期 / 设备离线 / 临时换秤（7天内绑定）/ 多人共用 / 未匹配到交易。
5. **投诉核验**：`regulator` → 投诉核验 → 核验属实（自动生成处罚）或驳回。
6. **处罚联动**：处罚确认 → 摊位信用 -10、市场信用 -2、近180天确认处罚≥3起的市场抽检频次升为「高频」、自动生成公示、关联投诉办结。
7. **申诉**：`vendor` 对已开出处罚提交申诉 → `regulator` 处理（成立则撤销处罚，驳回则恢复待确认）。
8. **整改闭环**：`vendor` 对已确认处罚提交整改 → 自动生成复检任务 → `regulator` 录入复检：合格则设备恢复使用、记录封签更换、整改闭环；仍超标则维持停用。
9. **监管档案**：任一秤的「监管档案」页汇总登记、抽检、停用、投诉、处罚、整改、复检、封签更换、回访全部事件时间线。
10. **追踪与年报**：`regulator` → 处罚后变化追踪（市场/摊位/设备/投诉人四维对比首次处罚前后90天投诉变化）；年度治理材料（抽检、超标、投诉、处罚、申诉、整改、公示、回访、信用分、抽检频次一屏汇总）。
11. **离线交易补传**：秤离线期间产生的本地流水，恢复网络时由市场管理方或本摊位摊主在「离线补传」页提交（离线窗口、设备本地时钟、封签状态、CSV 流水）。服务自动比对：
    - **本地流水 vs 服务器**：同一时间+重量的重复流水剔除，越界（不在离线窗口内）拒收；
    - **设备时钟 vs 服务器时间**：漂移超 5 分钟标记异常，超 30 分钟建议补做抽检；
    - **摊位绑定**：离线开始后才绑定当前摊位 → 换绑风险标记；
    - **封签状态**：补传时申报破损 → 异常标记；
    - **高峰期集中**：离线窗口落在早市 7-9 点 / 晚市 17-19 点的占比 ≥50% → 判定「异常集中」，自动生成**重点巡检任务**并扣减摊位信用 5 分。
    
    离线窗口内如有投诉，窗口内全部交易进入**人工复核**（监管「离线复核」队列：复核通过 / 标记可疑，可疑再扣信用 5 分）；补传完成后**重算窗口内全部交易可信度**（补传可信 / 待人工复核 / 复核通过 / 可疑），并给出**是否需要补做抽检**的提示（需要时自动生成抽检任务）。全部事件写入该秤监管档案。

## 演示数据预置状态

- 2 个市场、6 个摊位、6 台秤：含证书已过期（DEV-0002，停用中）、30天内到期+离线（DEV-0003）、多人共用（DEV-0004）、3天前临时换秤（DEV-0005）等场景；近 60 天模拟交易流水。
- 1 起已确认处罚（含公示）、1 起待确认投诉处罚、1 条待核验投诉、1 条待办复检任务，登录即可演示完整闭环。

## 目录结构

```
├── Dockerfile              # 多阶段构建：gradle 构建 fat-jar → temurin-jre 运行（非 root + HEALTHCHECK）
├── docker-compose.yml      # app + postgres（仅 app 发布端口）
├── .env.example
├── build.gradle.kts
└── src/main/kotlin/city/market/
    ├── Application.kt      # 会话、路由、静态资源、健康检查
    ├── auth/Auth.kt        # PBKDF2 口令散列、会话、角色
    ├── db/Tables.kt        # 16 张表：秤/交易/离线补传/抽检/投诉/处罚/申诉/整改/回访/公示/封签/档案事件…
    ├── db/Db.kt            # 连接池、建表、演示数据
    ├── service/Services.kt # 任务评分引擎、交易可信度判断、处罚联动、追踪/年度报表
    ├── service/OfflineSync.kt # 离线补传：四类比对、高峰异常、可信度重算、人工复核
    └── web/                # 四类角色页面路由（服务端渲染）
```

## 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` | `db/5432/scaleguard/...` | PostgreSQL 连接 |
| `PORT` | `8080` | 应用监听端口 |
| `UPLOAD_DIR` | `/app/uploads` | 封签/现场照片存储目录（compose 卷） |

| `SESSION_SECRET` | 开发默认值 | 会话签名密钥，生产必改 |
